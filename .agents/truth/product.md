# 产品决策

只保留重要且无法从代码直接读出的产品取舍；实现、测试与版本事实以仓库为准。

- renview 服务于 agent 主导开发时的人类审阅与代码理解，优先帮助人判断业务建模和抽象是否合理，因为人的逐行审核带宽有限。
- 简化的边界是是否影响业务抽象理解，而非是否改变运行时语义，因为语言类型、内存管理等工程机制可交给 agent，人仍需看清状态、规则与关键流程。
- 投影必须让人知道何处隐藏了信息并能取回原文，因为它是辅助理解的伪代码而非语义等价源码，信任来自可对照而非承诺无损。
- 常看的业务变化应直接可见，只有低频细节才折叠或下钻，因为理解主流程不应付出反复展开、收起的操作成本。
- 审阅以连续代码行流为主体，声明分类只辅助排序与定位，因为独立卡片和重复摘要会把人拉回逐单元核验并割裂上下文。
- 新增常驻元素必须证明它减少的认知成本大于占用的注意力，因为产品价值来自筛选与投影，参数追踪等验证工具不应挤占默认阅读路径。
- 默认分析应静态、离线且无需额外语言服务或 LLM，因为安装成本、冷启动和外部服务依赖会妨碍随时审阅，语义增强只能作为可选下钻。
- 当前阶段保持只读，反馈回到用户已有的 agent harness，因为评论、协作和审核状态管理会把工具扩张成另一套工作平台。
- 性能与交互优先服务单个 PR 的变更集和按需阅读文件，因为全仓索引与 monorepo 平台化会提前引入与核心场景不相称的复杂度。
